# M5 說明：聯動與發佈

M5 接上三個選用聯動包（樂牧、草本、酒館），補齊三語檢查，做了一輪平衡，打包成 1.0.0。開發流程見 [M1 說明](M1_說明.md)。

```
npm run balance    # 印出全部食物與飲品的平衡表；加 -- --write 另存成 docs/M5_平衡表.md
npm run build      # validate + test，打包成 dist/Kaleidoscope-Harvest-v1.0.0.mcaddon
```

## 聯動的共同做法

三個包都照 `api/cookery.js` 的模式：只送 Script Event，不 import 別的包的檔案；先等對方的 `api_ready`，確認 `capabilities` 裡有要用的項目才送；對方沒裝就什麼都不送，豐收照常可玩（企劃書「選用聯動」）。

- 三個包都只把註冊留在當次世界，所以每次載入都重新握手。樂牧與草本會在載入後主動廣播一次 `api_ready`，回應我們的 `api_ping` 時又送一次；兩邊的文件都說重送無害，所以每收到一次就重送一次。
- 對方的回覆是廣播給所有附加包的：樂牧的 `api_result` 只看 `id` 是 `kaleidoscope_harvest:` 開頭的，草本的 ack 只看 `to` 是我們的。
- 失敗只寫進內容記錄（`console.warn`，同一句只寫一次），不在畫面上顯示任何文字。
- 要送的內容全部在 `packs/BP/scripts/data/integrations.js`，每列附一句理由；`npm run validate` 會檢查這些物品都存在。

| 檔案 | 內容 |
| --- | --- |
| `api/ranching.js` | 樂牧握手與飼料註冊 |
| `api/herbal.js` | 草本握手、寒熱與佐使註冊 |
| `api/tavern.js` | 用酒館 SDK 註冊果酒 |
| `api/tavernSdk/` | 酒館的公開 SDK，從草本 1.1 原封不動複製（每個檔案開頭註明來源） |
| `data/integrations.js` | 飼料、寒熱、佐使、果酒的資料表 |
| `data/tavern.js` | 送給酒館的內容（配方與三語說明頁） |
| `data/version.js` | 版本號 `1.0.0`，手冊與酒館都讀這裡 |

## 樂牧：飼料

收到 `kaleidoscope_ranching:api_ready` 且 `capabilities` 有 `register_feed` 時，一筆一則送 `register_feed`。`ruminant`、`calcium` 兩種要 `feed_1_1`，目前沒用到。

| 物品 | 種類 | 份數 | 理由 |
| --- | --- | ---: | --- |
| 玉米 | grain | 2 | 整根玉米，份量足 |
| 玉米種子 | grain | 1 | 和小麥種子一樣 |
| 大豆 | grain | 1 | 豆類穀物飼料 |
| 豆渣 | mixed | 1 | 蛋白質高，算二級飼料；豆渣原本只有這個用途 |
| 大白菜 | veg | 2 | 整顆，份量大 |
| 青江菜、菠菜 | veg | 1 | 葉菜 |
| 白蘿蔔、地瓜 | veg | 2 | 根莖類，份量大 |

企劃書寫的是「送進飼料混合機做濃縮飼料」；樂牧 1.1 開放的是飼槽飼料（`register_feed`），沒有混合機配方 API，所以改成直接當飼料。

## 草本：寒熱與佐使

收到 `kaleidoscope_herbal:api_ready`（`api: 1`）後：

- 有 `external_heat`：送 `heat_register`，20 樣食物的寒熱值。草本自己的茶是 ±35～40、補品 +30～40，日常食物壓在 ±30 以內；只列中醫食療裡寒熱很明顯的（薑母茶、肉桂茶 +25，荔枝酒 +20，芒果冰 −30，梨類 −10～−15，黃瓜、柿子、香蕉 −10，滷味與羊肉串偏熱等）。完整清單與理由在 `data/integrations.js`。
- 有 `external_adjuvants`：送 `adjuvant_register`，只登記**陳皮**和**肉桂皮**兩樣，各 1 份。草本的佐使是所有模組共用 32 個名額，所以省著用；企劃書提到的薑和八角先不登記。
- 每封依 `limits.itemsPerMessage`（最多 32 筆）分批，並壓在 1800 字元內；目前寒熱一封約 1100 字元。
- 只處理 `sourceType` 是 `Server` 的回覆，和草本自己的規則一樣。

沒有複製草本的 `sdk/herbal-client.js`：豐收只登記、不查詢，直接照 `cookery.js` 的寫法送訊息比較短，也看得出送了什麼。

## 酒館：荔枝酒與桃子酒

酒館沒有文件，以草本 1.1 帶的公開 SDK 為準（`api/tavernSdk/`，三個檔案原樣複製）。payload 照草本 `data/tavernRecipes.js` 的欄位：

- `requires`：`barrel_recipes`、`guide_product_pages`、`chunk_transport`、`acknowledgements`，缺任何一項 SDK 就不送。
- `recipes`：荔枝酒、桃子酒兩條 `barrel` 配方。和草本的藥酒一樣是三種材料各一份、4 桶水、裝玻璃瓶、`unitTime` 4800：荔枝（桃子）＋糖＋小麥。
- `pages`：兩種酒的說明頁，加上荔枝、桃子的材料頁（讓酒館知道這兩種水果的名字），全部有繁中、簡中、英文。
- SDK 把整份內容切成 begin／chunk／commit 封包，每封不超過 1900 位元組（目前 8 封，最大約 1170），等到酒館的 `extension_ack` 才算完成。SDK 的成功訊息不記錄，只記錄失敗。
- 醃漬缸的果酒配方保留，沒裝酒館一樣做得出來。葡萄酒是酒館自己的，豐收只種葡萄，不登記任何葡萄相關的東西。

## 手冊

- 每個條目的說明現在明確帶三種語言（`mechanicsByLocale` 加上 `en_US`，和草本的手冊一樣），版本號改讀 `data/version.js`。
- 有聯動用途的物品多一行「裝了《樂牧》／《草本》／《酒館》時……」：飼料種類與份數、寒熱偏熱或偏涼、可當佐使、可用酒桶釀。沒裝那個包時，那個用途就不存在。

## 三語檢查

`npm run validate` 新增（邏輯在 `tools/lang.mjs`，測試也用同一份）：

- BP、RP 的語言檔：zh_TW 有的每個鍵，en_US 與 zh_CN 都要有而且不是空的；反過來也不能多出 zh_TW 沒有的鍵；同一個鍵不能出現兩次；`languages.json` 三種都要列。
- 手冊：每個條目三種語言的行數一樣、沒有空行；`names` 與 `text` 三種語言的鍵一樣（`language_note` 三種語言都刻意留空）。
- 酒館說明頁的標題與內文三種語言都要有，簡中不能留繁體字。

檢查跑起來時語言檔本身沒有缺漏。用 OpenCC 對照簡中時發現「叢林邊緣」的「緣」沒轉，已補進 `data/zh_cn.js`；新文字用到的「樂、館、釀、劑、飼、蓋、擺、檢、藥、圖、鑑、節」等字也一併補上。

## 平衡

`tools/balance.mjs` 列出全部 91 樣可吃的東西：飢餓、飽和係數、飽和、材料數、材料值、器具與時間。報表在 [M5 平衡表](M5_平衡表.md)。

材料值的算法：吃得了的豐收物品算它的飢餓值；生吃不了的作物算 2（約一根胡蘿蔔）；中間食材算做它的材料；原版材料以玩家本來會吃的樣子計（生肉以熟肉計、馬鈴薯以烤馬鈴薯計、雞蛋以廚房的煎蛋計）。

| 標記 | 意思 | 處理 |
| --- | --- | --- |
| ✗ over | 飢餓超過「材料值 ×1.5＋4」（烹調最多多給 4，比照馬鈴薯 → 烤馬鈴薯） | validate 失敗 |
| ✗ worse | 比單一可吃的材料還少（一次做多份時按份分攤） | validate 失敗 |
| △ loses | 飢餓加飽和比可吃材料的合計少 | 只列出 |

修正的離群值：

| 物品 | 原本 | 改成 | 原因 |
| --- | --- | --- | --- |
| 烤地瓜 | 6／0.7 | 5／0.6 | 一顆地瓜（1）丟進熔爐就給 6，比原版烤馬鈴薯還多；改成和烤馬鈴薯一樣 |
| 蒸地瓜 | 6／0.6 | 5／0.7 | 同上；要用廚房的蒸籠，飽和稍高 |
| 胡椒餅 | 7／0.7 | 9／0.7 | 用了一塊豬肉卻比直接烤豬排（8）還少 |
| 桃子酒 | 2／0.2 | 4／0.3 | 一瓶用掉一顆桃子（4）卻只給 2；封缸 5 天也該值得 |
| 荔枝酒 | 2／0.2 | 3／0.3 | 和桃子酒一致，略高於一顆荔枝 |

留下的 △ 有 18 項，主要是果汁、果酒（以保存換食物）和肉類料理（跟熟肉比；廚房自己的燉湯放了肉也只給 6）。豐收的料理整體比廚房保守（廚房炒菜多在 9～13），沒有往上調。

G4（每種作物至少兩個用途）仍由 validate 檢查，全部通過。

## 打包與版本

- 版本改成 1.0.0：兩個 manifest 的 header、模組與互相的相依、`package.json`、手冊的 `version`、送給酒館的 `version`。版本號只寫在 `data/version.js` 一處，validate 會檢查其他地方都一致。
- 打包改用 `tools/build.mjs`，用 Node 內建的 `zlib` 自己寫 zip，不再需要 `zip`、`python3` 或 `python`；`tools/build.sh` 只是轉呼叫它。`npm run build` 不再經過 bash。
- 產出 `dist/Kaleidoscope-Harvest-v1.0.0.mcaddon`，裡面是 `Kaleidoscope Harvest v1.0.0 [BP]/` 與 `[RP]/` 兩個資料夾，用 Python `zipfile` 讀過、CRC 檢查通過。

## 測試

`npm test` 新增 12 項（共 65 項）：

- 啟動時對三個包各送一次 `api_ping`，收到 `api_ready` 前什麼都不註冊。
- 樂牧：沒有 `register_feed` 或訊息壞掉時不送；有的話每種飼料一則，全部是自己命名空間、每則不到 2048 字元；第二次 `api_ready` 會重送。`api_result` 只記錄自己的失敗，同一句只記一次，聊天欄沒有文字。
- 草本：`api` 不是 1 或缺 capability 時不送；寒熱與佐使分開看 capability；照 `itemsPerMessage` 分批、不漏、不超過 2048 字元；佐使只有陳皮和肉桂皮；只記錄 `to` 是自己、由腳本送出的 ack。
- 酒館：payload 的配方、成品、材料都存在，沒有葡萄酒；封包是 begin／chunk／commit、每封不超過 1900 位元組，接回去就是原本的內容；SDK 沒拿到必要的 capability 不送，拿到後送出，收到 ack 就停，之後不再重送。
- 手冊三種語言行數一致，聯動用途有寫出來；語言檔檢查抓得到缺鍵、空值、多出的鍵；平衡沒有 ✗。

mock 新增 `system.clearRun`，`runTimeout` 會回傳編號（酒館 SDK 要用）。

## 需要進遊戲確認

- **樂牧**：九種飼料真的進得了飼槽、動物會吃；豆渣算混合飼料是否合理。
- **草本**：吃喝後寒熱有變化；陳皮、肉桂皮放進砂鍋會多一份；有沒有被別的模組先登記走（看內容記錄的 `TAKEN`）。
- **酒館**：酒館真的收下 payload（內容記錄沒有 `Rejected`）；酒桶認得豐收的材料並裝出豐收的荔枝酒、桃子酒；說明頁的圖示路徑 `textures/kaleidoscope_harvest/items/<id>` 酒館讀得到。酒館沒有文件，`category`、`recipeIds` 等欄位是照草本抄的；草本的藥酒可放地上，豐收的果酒不行，酒館若要求成品可放置需要另外處理。
- 三個包都裝時，握手順序與重送不會造成重複的東西（文件都說重送安全）。
- 改過數值的五樣食物在遊戲裡的飢餓與飽和。
- 用 1.0.0 的包覆蓋 0.1.0 的世界：版本號變了，遊戲應該當成同一個包的更新。
